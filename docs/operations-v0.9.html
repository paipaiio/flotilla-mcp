推荐路径

一次诊断，一次修复

1. 确认运行版本

flotilla --config /PATH/fleet.toml info

2. 批量检查凭证

flotilla --config /PATH/fleet.toml credentials all

3. 写入本机钥匙串

flotilla --config /PATH/fleet.toml credentials all --repair

4. MCP 内安全补全

credential-status { "target": "all", "repair": true }

5. 批量迁移到密钥

setup-repair { "target": "all" }

密码由隐藏输入读取并直接写入 OS Keychain；后续 SSH 尝试即时读取，无需重启 MCP。输出只显示来源和就绪状态。

凭证来源优先级

认证方式来源修复动作
password主机专用环境变量 → 通用环境变量 → OS Keychaincredentials TARGET --repair 或 MCP repair: true
keykeyRef 指向的可读密钥文件修正路径或权限
agent当前进程的 SSH_AUTH_SOCK确认启动环境继承 agent
URL 安全录入如何工作
  1. 缺少 SSH 密码时，支持 URL elicitation 的 MCP 客户端收到一个仅绑定 127.0.0.1 的一次性页面。
  2. 密码直接从浏览器表单写入 OS Keychain，不进入工具参数、结果、配置、日志或命令行。
  3. 页面提交后销毁一次性令牌；原来的 SSH 调用重新读取凭证并自动继续，不再要求手工重跑。

页面 10 分钟自动失效；并发请求同一账户时共用一次录入。未支持 URL elicitation 的客户端继续显示 CLI Keychain 修复命令。

SETUP / REPAIR

一次批准，批量迁移 password 节点

1 · 预览

解析 Target，只列出当前仍使用 auth = "password" 的节点；不生成密钥、不连接服务器、不修改配置。

setup-repair { "target": "group:prod" }

2 · 执行

一次审批覆盖整批。缺密码时复用本机安全页面，然后逐台安装同一把专用公钥。

setup-repair { "target": "group:prod", "apply": true }

3 · 验证与热重载

每台机器都用新的私钥重新建立连接；只有验证成功的节点才写入配置。配置完整校验、原子替换并热重载。

setup-repair { "target": "all", "apply": true, "removeStoredPasswords": true }
失败时会发生什么
  • 公钥安装或新密钥登录验证失败：该节点保持 auth = "password"。
  • 部分节点成功：只迁移验证成功的节点，并在结果中逐台列出原因。
  • 热重载失败：自动恢复原配置并重新加载；已安装的公钥保留，便于下次继续。
  • 默认保留 Keychain 密码作为回退；确认密钥稳定后再设置 removeStoredPasswords: true。

避免“改了源码却运行旧包”

runtime-info 和 CLI info 返回版本、模块路径、Node 可执行文件、有效配置路径、配置来源、服务器数量和钥匙串可用性。

flotilla --config /PATH/fleet.toml info

授权边界与默认审批

结构化 Shell 分析

识别引号、转义、管道、换行、环境变量包装和重定向；未知命令默认进入审批。

命令白名单

scopes.commands 只收窄角色权限，执行器在 SSH 前再次检查。

路径边界

scopes.paths 规范化路径并校验远端 realpath，阻止符号链接逃逸。

[servers.scopes]
commands = ["^systemctl status ", "^cat /opt/myapp/"]
paths = ["/opt/myapp/**"]

原始 exec、会话命令和用户提供的验证/健康命令按实际发送内容匹配；结构化工具自身生成的内部命令由 change-set 的路径/服务范围承接。

CHANGE SETONE APPROVAL

生产变更按资源范围审批，不再逐条拦内部命令

operator 可以提交结构化生产变更。config-apply、fleet-push 和 service-control 会生成稳定的 cs_… 标识，把目标、路径、服务、动作、回滚方式和载荷指纹绑定为一次审批。

目标与资源

审批卡明确列出 Target 主机、scopes.paths 路径和 scopes.services 服务；超出任一范围仍直接阻止。

精确载荷

配置值和上传文件只进入 SHA-256 指纹。相同路径换了内容会生成不同 change-set，旧 JIT grant 不会复用。

权限不扩散

viewer、readOnly、approvalMode = "deny" 保持关闭；operator 的生产 sudo 以及 admin 的生产 privileged 操作仍保持关闭。

CHANGE SET cs_0123456789abcdef
Targets: prod-1, prod-2
Paths: /etc/myapp/config.json
Services: myapp.service
Operations: set /server/port → restart → health-check
Rollback: restore backup → restart → health-check
审批后的执行边界

批准只覆盖卡片中的精确 change-set。工具自己生成的 cp/mv/systemctl/rc-service 命令由已批准的路径/服务范围承接；用户提供的验证与健康命令仍必须通过 scopes.commands 和内建禁用规则。原始 exec、会话命令不属于结构化变更，继续走逐命令策略。

单一执行前置链

命令工具统一经过同一条有序边界，避免漏掉 scope、审批、配额或审计。

1–2 · Resolve / Policy

解析目标，再按主机角色、环境层级、命令与路径 scope 决策。

3 · Approval

风险命令进入统一审批，支持短时 JIT grant。

4–5 · Quota / Audit

审批后消费配额，再下发 SSH 并记录聚合结果。

resolve → classify/policy → approval → quota/record → SSH → aggregate audit
已接入统一中间件的命令工具

exec-read、fleet-diff、exec、exec-sudo、signal-process。

LOCAL ONLYFINGERPRINT OUTPUT

敏感值只在可信本地流程与目标机内流转

配置密码、令牌和私钥字段使用 valueFromLocal。MCP 只收到字段路径、公开来源和指纹；值不会进入工具参数、审批卡、结果、审计或本机临时文件。

1 · 一次性本地录入

仅绑定 127.0.0.1，页面带 no-store、CSP、禁止嵌入和一次性随机令牌；提交或超时后立即失效。

config-apply { "target": "group:prod", "path": "/etc/myapp/config.json", "format": "json", "unit": "myapp", "changes": [{ "op": "set", "path": "/server/token", "valueFromLocal": true, "label": "API token" }], "apply": true }

2 · 内存 SFTP

原配置有界读取到进程内存，变更后直接写入目标机暂存路径；控制机不再创建包含配置内容的临时文件。

一次性本地页面 → 进程内存 → SHA-256 指纹 → 目标机

3 · 输出自动净化

公开上下文会保留，敏感片段替换为带 SHA-256 指纹和长度的占位符；相同值可关联排查，但不会返回原文。

API_TOKEN=[REDACTED secret-value sha256:0123456789abcdef length=32]
执行顺序与失败边界
  1. 先完成 Target、角色、路径、服务和自定义命令 scope 预检，再展示本地录入页。
  2. 录入值只保存在当前调用的进程内存中，并以 SHA-256 指纹绑定最终 change-set。
  3. 一次审批后通过内存 SFTP 写入目标机暂存文件，再执行验证、原子替换、重启和健康检查。
  4. 取消、超时、提交失败或事务结束都会清理一次性令牌和内存引用；页面不可重放。

常见敏感路径（password、secret、token、api-key、private-key、credential）拒绝字面量写法，必须选择 valueFromLocal: true 或 valueFromEnv。

信息边界

  • 诊断不返回密码、令牌或私钥内容。
  • 密码不进入命令行参数、配置文件和聊天文本。
  • 服务控制经过 scope、策略、审批与审计。
  • 重载清空服务管理器缓存并重新探测。

结构化配置变更，失败自动还原

config-apply 只接受 JSON Pointer 形式的 set/delete 变更。默认仅预览目标、字段路径与七阶段流程，不回显字段值，也不连接服务器。

1 · 预览变更

先确认 Target、远端路径、格式、服务和变更字段；字面量只显示为 source: literal。

config-apply { "target": "group:prod", "path": "/etc/myapp/config.json", "format": "json", "unit": "myapp", "changes": [{ "op": "set", "path": "/server/port", "value": 443 }] }

2 · 密钥从环境读取

敏感字段使用 valueFromEnv；结果和审计只记录字段路径与来源，不记录变量内容。

{ "op": "set", "path": "/server/token", "valueFromEnv": "MYAPP_TOKEN" }

3 · 一次审批执行

备份、暂存、结构验证、原子替换、服务重启和健康检查属于同一个批准动作。

config-apply { "target": "group:prod", "path": "/etc/myapp/config.json", "format": "json", "unit": "myapp", "changes": [{ "op": "delete", "path": "/legacy" }], "apply": true }
七阶段状态机
  1. 下载并在本机内存流程中解析原配置。
  2. 在目标机保留同目录备份。
  3. 上传同目录暂存文件。
  4. 重新解析结构，并可运行带 {file} 占位符的应用验证命令。
  5. 同目录 mv 原子替换。
  6. 自动适配 systemd/OpenRC，restart 或 reload 后执行健康检查。
  7. 安装后的任一步失败都会恢复备份、再次启动并复查旧版本。

成功结果会返回可审计的远端备份路径；中间暂存文件会清理；配置正文通过有界内存 SFTP 传输，不落控制机临时文件。

systemd / OpenRC 自动适配

每台主机默认 serviceManager = "auto"；首次服务操作做固定只读探测，混合集群按主机生成命令。

systemd

systemctl status UNIT
systemctl restart UNIT

OpenRC

rc-service NAME status
rc-service NAME restart

OpenRC 没有统一的逐服务 journal；使用 logs-tail --path 指定真实日志路径。

serviceManager = "openrc"
